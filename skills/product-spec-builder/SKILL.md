# Product Spec Builder

## 适用场景

- 用户描述新产品、新功能、需求、用户问题或改进想法。
- 用户知道大方向，但缺少边界、目标用户、验收标准或优先级。
- 开发前需要把口头想法整理成可执行规格。

## 输入要求

- 用户目标或问题描述。
- 已知约束、目标用户、平台、时间或技术背景。
- 如果信息不足，最多先问 3 个影响范围最大的澄清问题。

## 执行流程

1. 判断需求类型：新功能、改进、修复、实验、内部工具或发布配套。
2. 先做拷问，再写规格：逼用户对候选需求排序；必做项砍到最多 3 个，超过就让他删；问"只能上线一个选哪个"；逼他说出至少一件 v1 不做的事；逼他定一个可衡量的成功指标。在这五件事定下来前，不要急着输出规格。
3. 写之前先压力测试：逼用户列出"要让这事成立，什么必须为真"，按"最便宜、最能证伪的验证方式"排序，先验最致命的假设；再做一次 pre-mortem——"假设 v1 已经失败，最可能的原因是什么"，把最可能的一两个变成风险项或待确认问题，而不是含糊的担忧。
4. 提炼用户、场景、痛点、目标和非目标。
5. 补齐关键边界：必须做、暂不做、依赖、风险。
6. 定义用户流程和核心用例。
7. 写出验收标准，优先使用可验证语句。
8. 标注仍需确认的问题。
9. 输出产品规格草案；可用 `ai-pm-dev prd` 记录、`ai-pm-dev prd check --strict` 验证砍需求是否真的做了。

## 禁止事项

- 不直接写代码。
- 不接受一份没排序、没砍过的需求清单就开始写规格。
- 不在必做项超过 3 个时还往下走，先逼用户砍。
- 不为了显得好说话而跳过拷问；目标是逼出决定，不是附和。
- 不把不确定内容伪装成已确认事实。
- 不把 v0.2 或未来想法塞进 v0.1 范围。
- 不输出泛泛而谈的 PRD 套话。

## 输出格式

```markdown
# Product Spec

## 背景
## 目标用户
## 问题与目标
## 范围
## 非目标
## 用户流程
## 功能需求
## 验收标准
## 风险与依赖
## 待确认问题
```

## 验证标准

- 范围和非目标清楚。
- 验收标准可检查。
- 待确认问题不超过 5 个，且都影响执行。

## 停止条件

- 用户确认规格可以进入设计或开发计划。
- 仍有关键问题无法合理假设，需要用户回答。

## 维护文档 (Maintains)

负责维护项目操作层文档（位于 `docs/`）：

- `PROJECT_BRIEF.md` — 产品定位、目标用户、痛点、MVP 与非目标。

关键缺口写入 `open-questions.md`，不要用空泛文字填充。
