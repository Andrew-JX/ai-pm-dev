# Product Spec Builder

## 适用场景

- 用户描述新产品、新功能、需求、用户问题或改进想法。
- 用户知道大方向，但缺少边界、目标用户、验收标准或优先级。
- 开发前需要把口头想法整理成可执行规格。

## 输入要求

- 用户目标或问题描述。
- 已知约束、目标用户、平台、时间或技术背景。
- 如果信息不足，最多先问 3 个影响范围最大的澄清问题。

## 执行流程

1. 判断需求类型：新功能、改进、修复、实验、内部工具或发布配套。
2. 提炼用户、场景、痛点、目标和非目标。
3. 补齐关键边界：必须做、暂不做、依赖、风险。
4. 定义用户流程和核心用例。
5. 写出验收标准，优先使用可验证语句。
6. 标注仍需确认的问题。
7. 输出产品规格草案。

## 禁止事项

- 不直接写代码。
- 不把不确定内容伪装成已确认事实。
- 不把 v0.2 或未来想法塞进 v0.1 范围。
- 不输出泛泛而谈的 PRD 套话。

## 输出格式

```markdown
# Product Spec

## 背景
## 目标用户
## 问题与目标
## 范围
## 非目标
## 用户流程
## 功能需求
## 验收标准
## 风险与依赖
## 待确认问题
```

## 验证标准

- 范围和非目标清楚。
- 验收标准可检查。
- 待确认问题不超过 5 个，且都影响执行。

## 停止条件

- 用户确认规格可以进入设计或开发计划。
- 仍有关键问题无法合理假设，需要用户回答。

## 维护文档 (Maintains)

负责维护项目操作层文档（位于 `docs/`）：

- `PROJECT_BRIEF.md` — 产品定位、目标用户、痛点、MVP 与非目标。

关键缺口写入 `open-questions.md`，不要用空泛文字填充。
