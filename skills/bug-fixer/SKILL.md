# Bug Fixer

## 适用场景

- 报错、异常、测试失败、构建失败。
- 行为和预期不一致。
- 最近改动造成回归。

## 输入要求

- 错误信息、复现步骤、期望行为和实际行为。
- 如果用户没有提供，先从代码、日志、测试或命令中收集证据。

## 执行流程

1. 记录症状和已知事实。
2. 尝试复现或收集最接近的证据（报错、日志、失败的测试）。
3. **先分层判断**：问题更像前端、后端、数据库、配置还是依赖？沿日志、运行环境和底层依赖一层层定位，不要只盯业务代码或自己负责的那块。
4. **系统性收窄**：用二分排查（逐个关闭/启用模块、缩小输入范围）锁定触发点，而不是凭猜测大改。
5. 提出最小假设并验证。
6. 做最小修复。
7. 运行回归验证，并尽量加一个**回归护栏**（一个测试或检查），让同样的问题不再悄悄回来。
8. 用 `ai-pm-dev pitfall` 把可复用的坑追加进 `docs/troubleshooting.md`（症状、根因、修复、验证）。
9. 总结根因、修复和测试结果。

## 禁止事项

- 不先猜测然后大改。
- 不只看业务代码或自己负责的模块，要沿日志、运行环境和依赖一层层查。
- 不用掩盖错误代替修复根因。
- 不删除测试来让结果变绿。
- 不在没有证据时宣称找到根因。
- 不把环境、编码、端口、配置漂移等系统性问题只当作一次性错误处理。

## 输出格式

```markdown
# Bug Fix Report

## 症状
## 复现或证据
## 根因
## 修复
## 验证
## 记录更新
## 剩余风险
```

## 验证标准

- 至少有复现、日志、测试失败或代码证据之一。
- 修复范围最小。
- 回归验证覆盖原问题。

## 停止条件

- bug 修复并验证完成。
- 无法复现且缺少继续判断的关键证据。

## 维护文档 (Maintains)

负责维护项目操作层文档（位于 `docs/`）：

- `troubleshooting.md` — 每次修复非显而易见的 bug 后追加：症状、根因、修复、验证。
