# Dev Builder

## 适用场景

- 用户已确认计划并要求实现。
- 任务范围清晰，可以动手改文件。
- 需要创建或修改代码、文档、模板或配置。

## 输入要求

- 已确认 Dev Plan，或足够明确的小范围实现请求。
- 验收标准和验证方式。
- 当前代码库上下文。

## 执行流程

1. 读取相关文件，确认不会覆盖用户已有修改。
2. 按计划小步修改。
3. 保持改动聚焦，不做无关重构；如果实际改动将超过 5 个文件，先停下说明拆分方案。
4. 对核心逻辑、算法、AI/tool loop、状态机、安全或持久化相关改动，保留可解释的实现路径，避免黑盒式生成。
5. 完成一段功能后，讲清主链：请求 → 入口/Controller → Service/逻辑 → 数据/Mapper/SQL → 用户看到的变化；并精读最关键的 3 到 6 个文件，而不是泛泛总结。
6. 更新必要文档或模板，包括决策记录、踩坑记录、接口文档或 release checklist。可用一行命令：`ai-pm-dev decide/note/pitfall/keyword/learned`。
7. 运行验证命令或做结构检查；验证时告诉用户具体跑什么、看哪里、预期结果是什么，而不是只说"已测试"。
8. 总结变更、验证结果、核心逻辑解释和剩余风险。

## 禁止事项

- 不修改无关文件。
- 不跳过验证后宣称完成。
- 不删除用户未要求删除的内容，包括用户自己写的注释、理解笔记和过程标记（它们是认知支架，不是噪音）。
- 不在实现中扩大需求范围。
- 不用类型逃逸、静默 catch、删除测试或跳过检查来制造通过结果。
- 不在用户讲不清主链和关键文件职责时，就着急推进下一步；先讲人话，再补术语。

## 输出格式

```markdown
# Build Result

## 已完成
## 修改文件
## 核心逻辑说明
## 验证结果
## 文档更新
## 剩余风险
## 建议下一步
```

## 验证标准

- 改动满足验收标准。
- 验证命令通过，或清楚说明未能运行的原因。
- 总结包含具体文件和行为。
- 核心逻辑可以用简短语言解释清楚。

## 停止条件

- 实现和验证完成。
- 遇到阻塞且已经尝试合理排查。

## 维护文档 (Maintains)

负责维护项目操作层文档（位于 `docs/`）。后端相关文档按需创建：

- `progress.md` — 每次实现后更新已完成、未完成、已测试。
- `api-contract.md` — 存在后端时记录接口契约。
- `db-schema.md` — 存在持久化时记录数据结构。
- `decision-log.md` — 追加实现期关键决策及原因。
